# 《飞行小八戒》V1 技术设计文档

## 1. 技术基线

- 引擎：Cocos Creator `3.8 LTS`，创建工程时锁定具体补丁版本并提交版本说明。
- 语言：TypeScript，开启严格类型检查所需规则。
- 平台：微信小游戏；浏览器预览仅用于快速调试，不作为最终兼容性结论。
- 画面：2D、竖屏、设计分辨率 `750 × 1334`，适配安全区与长屏。
- 物理：V1 使用自定义运动学与简单 2D 碰撞体，不引入重量级刚体模拟。
- 官方参考：[Cocos Creator 3.8 LTS 手册](https://docs.cocos.com/creator/3.8/manual/zh/)；[发布到微信小游戏](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-wechatgame.html)。

正式发布前重新核对微信包体、基础库和审核要求；这些平台规则可能变化，不把当前数值写死在业务代码中。

## 2. 架构目标

- 核心规则与 Cocos 节点表现分离，便于测试和调参。
- 所有玩法数值集中配置，不散落在组件脚本里。
- 障碍物重复复用，不在游玩过程中频繁实例化和销毁。
- 状态切换有唯一入口，避免死亡后仍计分、暂停后仍生成等竞态。
- 角色碰撞后锁定输入、碰撞和计分，依次播放 `hit → dead`；死亡最后一帧保持，使用独立死亡重力掉出底部。离屏事件触发结算，`1.5 s` 为异常保护上限。
- `fall` 使用速度与时间双阈值：`velocityY <= -260 px/s` 且持续 `0.16 s`，正常点击间隙保持 `fly_up`，避免动画抖动。
- 微信平台能力通过适配层调用，不让业务代码直接到处调用 `wx.*`。

## 4. 核心模块

| 模块 | 职责 |
| --- | --- |
| `GameFlow` | Boot/Home/Ready/Playing/Paused/GameOver 状态机 |
| `InputController` | 将触摸/鼠标按下边沿映射为单次 `flap` 动作，处理抬起、取消和生命周期清理 |
| `PlayerFlight` | 点击冲量、重力、速度上限、位置边界和表现参数 |
| `ObstacleSpawner` | 根据难度与安全规则生成障碍组 |
| `ObstacleGroup` | 管理上下障碍、计分门、激活和回收 |
| `ObstacleMotion` | 火球、雷电、风火轮的可预测运动 |
| `CollisionService` | 玩家与危险边界、障碍的碰撞结果 |
| `ScoreService` | 单局分数、最高分和一次性计分 |
| `PoolService` | 障碍、特效与浮字对象池 |
| `AudioService` | BGM、音效、静音状态和前后台恢复 |
| `StorageService` | 本地最高分、设置的版本化读写 |
| `PlatformBridge` | 微信生命周期、安全区与平台能力适配 |
| `DifficultyService` | 根据分数输出当前难度档配置 |

M5 当前运行 BGM 为 `assets/resources/audio/music/bgm_journey_clouds_lyrical.wav`，通过 `GameAudio` 的 Music 分组循环播放；首次有效起飞后启动，暂停、撞击和切后台时暂停或停止。该曲为项目原创东方神话氛围音乐；优美版采用更慢的 90 BPM、呼吸式主旋律、低音区应答、持续和声及稀疏点缀，不依赖第三方《西游记》配乐授权。

## 5. 场景节点建议

```text
GameRoot
  BackgroundRoot
    SkyLayer
    FarLayer
    MidLayer
    NearCloudLayer
  GameplayRoot
    ObstacleRoot
    PlayerRoot
    EffectRoot
  UIRoot
    HomePanel
    HUDPanel
    PausePanel
    ResultPanel
    SafeArea
  Services
```

玩法节点与 UI 节点分层；暂停玩法时 UI 仍须响应。不要通过搜索节点名称驱动业务，依赖使用序列化引用或明确注入。

背景采用固定天空底色加三层单实例视差：远景天宫、中景云、近景云分别进行低、中、高幅度的横向漂移，并保留低幅垂直浮动。V4 透明层没有无缝平铺边缘，不得创建整幅画布副本首尾拼接；各层通过放大留出运动余量，横向位移严格限制在素材仍能覆盖视口的安全范围内，`BackgroundRoot` 的矩形 Mask 负责裁掉屏幕外内容。Ready 状态以正常速度的约 `28%` 慢速运动，Playing 使用正常速度，Paused 和死亡阶段停止，重开恢复 Ready 速度。若后续需要永久单向循环，必须先制作边缘可平铺素材或真正独立的云朵/天宫小图。

## 6. 飞行模型

每个逻辑帧：

```text
if flapPressedThisFrame:
    velocityY = flapVelocity
else:
    velocityY = clamp(velocityY + gravity * dt, maxFallSpeed, maxRiseSpeed)
positionY += velocityY * dt
```

- `dt` 应限制最大值，避免切后台或卡顿后一帧穿透障碍。
- 输入层只产生一次性 `flapPressed` 动作；持续按住不得每帧重复触发。
- `Touch Start / Pointer Down` 捕获按下边沿；`Touch End / Touch Cancel` 只负责释放触点和清理状态。
- 多点触摸在同一逻辑帧最多消费一次 `flap`，避免双指同时落下造成双冲量。
- 点击冲量只修改垂直速度，不直接修改位置。
- 视觉倾角由速度平滑映射；碰撞体不随耳朵逐帧形变。
- 首次点击开始时直接应用 `flapVelocity`，避免待机浮动值污染正式运动。

## 7. 障碍生成算法

1. 从当前难度档读取速度、间距、通道高度和动态障碍权重。
2. 选择地面/天空障碍类型，应用组合白名单与冷却规则。
3. 在允许范围内抽取通道中心高度。
4. 限制该中心与上一组中心的最大差值。
5. 计算两侧素材尺寸、动态位移包络与实际碰撞体。
6. 验证最窄时刻仍满足最低通道要求；失败则重新采样，最多有限次数。
7. 仍不合法时回退到安全静态组合，绝不能无限循环。
8. 从对象池取出障碍组并激活。

随机数入口应可注入种子，便于复现“某一局出现无解组合”的问题。

## 8. 动态障碍状态

- 火球：固定起点和终点之间做正弦往返；对象激活时重置相位。
- 雷电：`Warning → Active → Cooldown`，只有 Active 阶段碰撞体生效。
- 风火轮：视觉持续旋转；位移可选正弦往返，碰撞体使用稳定圆形或多边形近似。
- 动态逻辑在暂停和 GameOver 时停止。

## 9. 碰撞与公平性

- 八戒使用一个稳定的胶囊形、圆形或圆角矩形核心碰撞体，不把耳朵最外缘全部算入死亡判定。
- 山峰和石柱使用简化多边形/矩形；火球、风火轮优先圆形；雷电使用明确矩形或线段包络。
- 碰撞体应比可见危险主体内缩约 `5%～12%`，具体以试玩为准。
- 高速运动时采用分段检测或扫掠思路，防止一帧跨过薄障碍。
- 计分门与伤害碰撞分层，不能互相触发。

## 10. 对象池与生命周期

- 障碍组在屏幕右侧激活，移动到左侧回收线后回池。
- `reuse()` 必须重置位置、缩放、计分标记、动画相位、碰撞启用状态和事件订阅。
- `unuse()` 必须停止 tween、计时器、粒子和音频。
- 游戏重开调用统一的 `resetRun()`，不得依赖重新加载整个场景才能恢复正确状态。

## 11. 配置数据

所有可调值集中在 `GameBalanceConfig`：

- 点击起飞速度、点击最短间隔、重力、速度上限、倾角。
- 障碍速度、生成距离、通道高度、中心变化上限。
- 每个障碍的尺寸档、碰撞内缩、运动周期和幅度。
- 难度档阈值、组合权重、组合禁用规则。
- 动画、受击停顿、震屏、音量等表现参数。

V1 运行时音频策略为 BGM、得分与撞击三类；连续点击和雷电状态不加载、不播放音效，只保留视觉反馈。

开发环境应能打印当前种子和难度档，并提供碰撞体/安全通道调试显示；发布版关闭。

## 12. 本地存储

建议数据：

```ts
interface LocalSaveV1 {
  schemaVersion: 1;
  bestScore: number;
  musicEnabled: boolean;
  sfxEnabled: boolean;
}
```

- 读取异常时回退默认值，不让游戏崩溃。
- 未来升级通过 `schemaVersion` 迁移。
- 只在最高分变化或设置变化时写入，避免每帧写存储。

## 13. 微信适配

- 监听前后台切换，进后台立刻暂停并停止音频。
- 使用安全区信息调整顶部 HUD 和底部按钮。
- 真机验证触摸取消、电话/弹窗打断、音频恢复和长屏布局。
- V1 不接开放数据域、广告与云能力。
- 资源优先压缩进核心包；资源明显增长后再规划 Asset Bundle/分包。

## 14. 性能目标

- 目标：常见中档微信真机稳定 `60 FPS`；无法稳定时至少维持平稳 `30 FPS`，不频繁跳变。
- 游戏过程不应持续创建临时节点、材质或大对象。
- 合理合图，控制透明叠加面积和粒子数量。
- 背景循环复用，避免无限拼接节点。
- 连续运行 10 分钟后节点数和内存不应持续单向增长。

## 15. 测试切面

- 纯逻辑：速度积分、难度选择、组合过滤、中心高度约束、计分幂等、存储迁移。
- 编辑器：节点引用、预制体重置、碰撞层、动画事件。
- 微信开发者工具：构建、生命周期、分辨率与日志。
- 真机：触控延迟、帧率、音频、刘海/圆角安全区、长时间稳定性。
